# Tools Framework (tools-core + tools-core-macros)

## Purpose

The `tools-core` crate (Layer 3) defines the foundational abstractions for the tool system: the `Tool` trait, typed execution, JSON schema generation, parameter extraction, the tool registry, permissions, and the feature package system. The companion `tools-core-macros` crate provides derive macros that eliminate boilerplate when building tools and feature packages.

Together they form the framework that all tool implementations (filesystem, web, calendar, todo, etc.) build on top of.

## Key Types

### Tool Trait

The primary interface for all agent tools. Every tool implements:

- `name()` -- machine-readable name used in LLM function calls (e.g., `"read_file"`).
- `description()` -- human-readable description shown to the LLM.
- `parameters()` -- JSON Schema describing the tool's parameters.
- `execute(args, ctx)` -- async execution with untyped JSON arguments and a routing context.
- `permission_level()` -- returns the required `PermissionLevel` (defaults to `Standard`).
- `to_schema()` -- generates the OpenAI function-calling format envelope.
- `validate_params(params)` -- validates a JSON value against the parameters schema, supporting type checks, required fields, enum constraints, oneOf/anyOf, patterns, min/max, and additionalProperties.

`DynTool` is the type alias `Arc<dyn Tool>` used throughout the registry.

### ToolExecute Trait

The typed execution interface. Tools implement this with a concrete `Params` type (which must implement `ToolParams`), then use `#[derive(Tool)]` to bridge the untyped `Tool` trait:

```rust
#[async_trait]
pub trait ToolExecute: Send + Sync {
    type Params: ToolParams;
    async fn execute(&self, params: Self::Params, ctx: &RoutingContext) -> Result<String>;
}
```

### ToolParams Trait

Typed parameter interface for JSON schema generation and parsing:

```rust
pub trait ToolParams: Sized {
    fn json_schema() -> Value;
    fn from_args(args: Value) -> Result<Self>;
}
```

Implementations are generated by `#[derive(ToolParams)]`.

### RoutingContext

Carries per-invocation context through tool execution:

- `channel` -- which platform the request came from (Telegram, Discord, CLI, etc.).
- `chat_id` -- conversation identifier.
- `interaction_tx` -- optional oneshot channel for the ask_user tool (CLI/dashboard mode).
- `is_direct_mode` -- when true, the user receives responses via an event stream rather than the message bus.
- `entity_tx` -- channel for tools to emit entity cards (e.g., after creating a task).
- `interaction_channel` -- optional platform-native interaction channel (Telegram buttons, Discord selects).

### InteractionChannel Trait

Defined in tools-core to avoid circular deps with the channels crate. Channel implementations that support native UI elements (Telegram inline keyboards, Discord buttons/selects, Slack Block Kit) implement this trait. The ask_user tool checks for this before falling back to text-based interaction.

### PermissionLevel and ToolPermissions

Four ordered permission levels: `ReadOnly`, `Standard`, `Elevated`, `Admin`. Each tool declares its required level. `ToolPermissions` maps per-channel permission grants -- when configured, the registry checks `is_allowed(channel, required)` before executing a tool. When no permissions are configured, all tools are allowed (backward-compatible).

### ToolRegistry

Central storage and dispatch for registered tools:

- `register(tool)` / `register_dyn(tool)` -- add a tool (static or pre-wrapped dynamic).
- `get(name)` -- look up by name, returns `Option<DynTool>`.
- `get_definitions()` -- returns `Arc<Vec<Value>>` of all tool schemas in OpenAI format. Cached internally with interior mutability; cache invalidated on registration/unregistration.
- `execute(name, params, ctx)` -- look up, check permissions, validate params, execute. Logs warnings on failure.

### FeaturePackage Trait

Abstraction for self-contained features that bundle tools, migrations, config, and health checks:

- `name()` -- unique feature name (e.g., "todo", "finance").
- `tools()` -- the `DynTool` instances this feature provides.
- `migrations()` -- SQL migrations owned by this feature (`FeatureMigration` with version ordering).
- `config_key()` / `default_config()` -- config section management.
- `health_check()` -- returns `HealthStatus` (Healthy, Degraded, or Unhealthy).

### ParamExtractor

Zero-cost wrapper around `&Value` for ergonomic parameter extraction. Eliminates the repetitive `args.get("x").and_then(|v| v.as_str()).ok_or_else(...)` pattern:

- `required_str`, `required_i64`, `required_u64`, `required_bool`, `required_array`, `required_object` -- return `Err` if absent or wrong type.
- `optional_str`, `optional_i64`, `optional_f64`, `optional_bool`, `optional_array` -- return `Ok(None)` if absent, `Err` if present but wrong type.
- `str_or`, `i64_or` -- return a default if absent.
- `string_array_or_empty` -- extract string array, silently filtering non-string elements.

### ConfigPersistence Trait

Runtime config persistence for feature packages. Implementations live in the agent or CLI crate, features receive `Arc<dyn ConfigPersistence>` to `load_section` and `save_section` without depending on the config crate directly.

### Page

Generic cursor-based pagination container for tool list operations. Contains `items`, an optional `cursor` string, and `has_more` flag.

### Searchable and rrf_merge

`Searchable` is a trait requiring `search_id() -> &str` for items that participate in search. `rrf_merge` implements Reciprocal Rank Fusion to merge keyword and semantic search results into a single ranked list with source attribution ("keyword", "semantic", or "both").

## Derive Macros (tools-core-macros)

### #[derive(Tool)]

Generates the full `Tool` trait implementation from struct metadata:

```rust
#[derive(Tool)]
#[tool(
    name = "read_file",
    description = "Read the contents of a file.",
    params = "ReadFileParams",
    permission = "read_only"    // optional, defaults to Standard
)]
pub struct ReadFileTool { ... }
```

Requires the struct to implement `ToolExecute<Params = ReadFileParams>`. The generated `Tool::execute` parses JSON args via `ToolParams::from_args`, then delegates to `ToolExecute::execute`.

### #[derive(ToolParams)]

Generates the `ToolParams` trait implementation (json_schema + from_args) for a parameter struct:

```rust
#[derive(Debug, ToolParams)]
pub struct ReadFileParams {
    /// The file path to read
    #[param(required)]
    pub path: String,

    /// Maximum characters to return
    #[param(min = 100)]
    pub max_chars: Option<i64>,
}
```

- Doc comments become JSON schema `description` fields.
- `#[param(required)]` adds the field to the `required` array.
- `#[param(min = N, max = N)]` adds `minimum`/`maximum` constraints.
- `#[param(min_length = N, max_length = N)]` adds string length constraints.
- Supported types: `String`, `bool`, integers (u8-u64, i8-i64), floats (f32, f64), `Vec<String>`, and `Option<T>` for any of the above.

### #[derive(ActionParams)]

Similar to `ToolParams` but generates inherent methods (`json_schema()`, `from_value()`) instead of a trait impl. Used for per-action parameter structs in multi-action tools.

### #[tool_actions]

Attribute macro for multi-action tools. Generates the `Tool` trait impl with action-based dispatch:

```rust
#[tool_actions(name = "todo", description = "Manage tasks.")]
impl TodoTool {
    #[action(name = "add")]
    async fn add(&self, params: AddParams, ctx: &RoutingContext) -> Result<String> { ... }

    #[action(name = "list")]
    async fn list(&self, params: ListParams, ctx: &RoutingContext) -> Result<String> { ... }
}
```

Generates:
- A combined parameters schema with an `action` enum and merged properties from all action param types.
- An `execute` method that extracts the `action` field, parses action-specific params, and dispatches to the corresponding method.

### #[derive(DomainEnum)]

Generates `as_str()`, `from_str_loose()` (case-insensitive), `Display`, and `FromStr` for unit enums. Supports PascalCase-to-snake_case conversion, `#[canonical("custom")]` overrides, and `#[aliases("alt1", "alt2")]` for alternative names:

```rust
#[derive(DomainEnum)]
enum Priority {
    High,
    #[aliases("med", "medium")]
    Medium,
    Low,
}
```

## How It Works

### Creating a New Tool

**Single-action tool (derive approach):**

1. Define a params struct with `#[derive(ToolParams)]`.
2. Define a tool struct with `#[derive(Tool)]` and metadata attributes.
3. Implement `ToolExecute` with the typed params.
4. Register with `registry.register(MyTool::new(...))`.

**Multi-action tool (attribute approach):**

1. Define per-action params structs with `#[derive(ActionParams)]`.
2. Define the tool struct with action methods annotated `#[action(name = "...")]`.
3. Apply `#[tool_actions(name = "...", description = "...")]` to the impl block.
4. Register the same way.

**Manual implementation** is also possible by implementing the `Tool` trait directly, as done for `BrowserTool`, `SpawnTool`, `CronTool`, and others that need complex parameter schemas or dynamic behavior.

### Execution Flow

```
LLM function call (name, JSON args)
    |
    v
ToolRegistry::execute(name, args, ctx)
    |
    +-- Look up tool by name (HashMap)
    +-- Check permissions (channel level >= tool's required level)
    +-- Validate params against JSON schema
    +-- Call tool.execute(args, ctx)
            |
            +-- [Derived tools] Parse JSON to typed params via ToolParams::from_args
            +-- [Derived tools] Delegate to ToolExecute::execute(params, ctx)
            +-- [Action tools] Extract action, parse action-specific params, dispatch
            +-- [Manual tools] Handle directly
    |
    v
Result<String> returned to agent loop
```

### Type Classification

The helpers module (`helpers.rs`) classifies Rust types into JSON schema types at compile time. `String` maps to `"string"`, `bool` to `"boolean"`, integer types to `"integer"`, float types to `"number"`, `Vec<T>` to `"array"`, and `Option<T>` extracts the inner type and marks the field as optional. Unknown types fall back to `"string"`.

## Connections

**Depends on:**
- `common` (Layer 0) -- error types (`KlyntbotError`, `ToolError`), `ChannelName`, `ChatId`, interaction types
- `async-trait` -- for async trait definitions
- `serde_json` -- JSON value manipulation
- `regex` -- for schema pattern validation
- `syn`, `quote`, `proc-macro2` -- macro implementation (macros crate only)

**Depended on by:**
- `tools` (Layer 3) -- all tool implementations build on this framework
- `feature-todo`, `feature-finance` -- feature packages use `ToolParams`, `Tool`, `FeaturePackage`
- `agent` (Layer 5) -- owns the `ToolRegistry`, registers tools, calls `execute`
- `channels` (Layer 4) -- channel impls may implement `InteractionChannel`
