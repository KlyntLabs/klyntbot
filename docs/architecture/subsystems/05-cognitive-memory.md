## TL;DR

KlyntBot's memory system. **`cognitive`** is the largest single crate in the workspace and the most intricate: it implements semantic + episodic memory, FSRS-5 spaced repetition, Louvain community detection (394-line first-party impl), Personalized PageRank retrieval (404-line first-party impl), the reforge nightly cycle (16 phase markers, 3 LLM calls at the handler level, 6 extension hook traits), and the mirror engine (8–10 signal sources feeding a self-reflection facade). **`ai-core`** is the trait system that lets feature crates declare LLM-routable events / entities / recall providers with minimal boilerplate; **`ai-core-macros`** generates the impls. **`autotuner`** runs A/B-style trials on agent parameters (prompts, weights, thresholds) with constraint-based promotion.

This is also the subsystem with the most env-gated feature flags (`KCA_*`) and the deepest extension surface — `run_reforge` alone takes 25 parameters, many of which are `Option<&dyn Trait>` hooks.

## Mental model

Cognitive memory is **layered, not flat**:

1. **Signals** (the lifecycle entry). Every feature emits events on the `DomainEventBus`. `SignalRouter` translates each event into an `AiSignal` (via per-feature `Translator` closures generated by `#[derive(AiEvent)]`). Signal consumers (cognitive ingestion, mirror sources, metric harvest) react asynchronously.
2. **Per-signal extraction**. Signals classified as `SalienceVerdict::Extract` go through `ExtractionHandler` (LLM-backed) to produce `ExtractedFact`, `ExtractedEntity`, `ExtractedRelationship`. `Accumulate` signals merge into existing aggregates; `Discard` signals are dropped.
3. **Persistence**. Repos (`SemanticFactRepo`, `EpisodicMemoryRepo`, `KnowledgeAtomRepo`, `EntityRepo`, `CommunityRepo`, etc.) write to SQLite; embedding-backed services write to LanceDB.
4. **Retrieval**. `UnifiedMemoryService` combines embedding-based ANN search + BM25 + Personalized PageRank graph boost. `ConversationRecallService` adds session-aware filtering. `CognitiveContextSource` wraps everything for context injection at LLM-call time.
5. **Reflection** (`mirror`). `MirrorEngine` runs 8–10 signal sources that observe runtime behavior, persist mirror state, and expose a `MirrorFacade` for the UI/MCP layer.
6. **Self-improvement** (`reforge`). A nightly 16-phase cycle reads behavioral feedback, synthesizes rewrites of strategy files, persists `reforge_suggestions`, and (via extension hooks) consolidates the knowledge graph and analyzes communities.
7. **Trial system** (`autotuner`). Independent A/B-style experimentation. Trials get scored on 13 metrics; promotion is gated by `ConstraintEvaluator`.

### The single biggest non-obvious thing

**Two functions named `retrievability` with completely different formulas:**

| Function | Formula | Used for |
|---|---|---|
| `cognitive::services::fsrs5::retrievability(elapsed_days, stability)` | Power-law: `1 / (1 + t/(9S))` | Flashcard scheduling (`FlashcardRepo`, `FsrsParamsRepo`) |
| `cognitive::services::decay::retrievability(elapsed_days, stability)` | Exponential: `exp(ln(0.9) * t/s)` | Retrieval-time relevance scoring (12-factor `RelevanceWeights`) |

They serve different subsystems. If you grep `retrievability(` and import the wrong one, the bug will be silent and show up months later as wrong recall ranking or wrong flashcard intervals.

### The second biggest non-obvious thing

**Two distinct `AutotunerBridge` traits with the same name:**

- `cognitive/services/reforge/mod.rs::AutotunerBridge` — for Phase 6 trial orchestration (`run_evaluation`, `create_trials`).
- `cognitive/mirror/types.rs::AutotunerBridge` — for `MirrorFacade`'s champion-promotion flow.

Same name, different responsibilities, different methods. Concrete implementations live in `app-core` to avoid circular deps.

Both pure algorithms, no LLM, no async DB inside core functions.

Called inline by `services/scoring.rs:126` during retrieval scoring AND by `services/community_intelligence/mod.rs:244` during Phase 6.5b split analysis. **Not called from `run_reforge` directly** — invoked at the scoring + community-planner layer.

## Workflows

### Signal lifecycle — event to memory

```
1. Feature publishes DomainEvent::Whatever via DomainEventBus
2. SignalRouter receives via broadcast::Receiver
3. Translator closure: DomainEvent → Option<AiSignal>
   (closure generated by #[derive(AiEvent)])
4. Salience decision (AiSignal.salience):
   - Extract → push to extraction pipeline
   - Accumulate → merge into AccumulatedObservationRepo
   - Discard → no-op
5. ExtractionHandler (LLM-backed): produces ExtractedFact/Entity/Relationship
6. ExtractionCritic (LLM-backed): scores facts; rejects low-quality
7. ConsolidationHandler::execute_memory_ops:
   - SemanticFactRepo.upsert (bi-temporal)
   - EpisodicMemoryRepo.insert
   - EntityRepo.upsert + CoActivationRepo edges
8. (Async) Embedding into LanceDB via SemanticFactEmbedder
9. (Periodic) Community detection (Louvain) via Phase 6.5b
10. (Nightly) Reforge synthesizes rule rewrites
```

### Retrieval (assistant turn)

```
1. AgentRuntime calls ContextEngine::prefetch_memory(message, session_key, ctx)
2. UnifiedMemoryService.search:
   a. Embed query → ANN search via LanceDB (top-K candidates)
   b. BM25 score same candidates from SemanticFactRepo
   c. Reciprocal Rank Fusion (RRF) merge
   d. PPR boost using CachedPprGraph (additive)
3. ConversationRecallService filters by session relevance
4. CognitiveContextSource formats as prompt-ready strings
5. Returned via ContextSource::provide()
```

### Reforge nightly cycle (full)

See [the 16-phase table above](#the-reforge-cycle--all-16-phases). Cron registered in `app-core/src/init/cron.rs::JOB_REFORGE_NIGHTLY` (03:00 local).

Phase 6.5 (Graph Consolidation) and 6.5b (Community Intelligence) only run if their hooks are installed. Phases 6.7 and 7.7 are env-flag gated.

### Mirror lifecycle

```
1. MirrorEngine::start(repo, narrative_handler, autotuner_bridge,
                       episodic_repo, rule_repo, trial_evaluator,
                       approval_history_repo, approval_pattern_repo,
                       bash_repo)
   - Constructs 8 unconditional signal sources
   - Conditionally constructs 2 more if optional repos are Some
   - Wraps each in MirrorSubscriberRunner
   - Returns StartedMirror { facade, consumers, flush_handles, shutdown }

2. CALLER MUST STORE the StartedMirror — dropping flush_handles cancels flushers.
   AppCore holds it as Option<StartedMirror>.

3. Signal sources accumulate observations in memory and periodically flush to MirrorRepo.

4. MirrorFacade exposed via Tauri commands + MCP MirrorTool for queries and feedback.
```

## Internals

### Why `run_reforge` has 25 parameters

The cycle was originally a tight 8-phase function. As community-intelligence, graph-enrichment, coding-specific phases, cross-CLI transfer, and skill discovery were added as **extension points** rather than core logic, each landed as a new `Option<&dyn Trait>` parameter. The current signature reflects this organic growth.

Trade-off: very flexible (anyone can install / omit hooks), very ugly. A future refactor could pack the parameters into a `ReforgeContext` builder. **Has not been done.**

### Why `KCA_COMMUNITY_SUMMARIES` / `KCA_REFORGE_COMPRESS` are env-gated

Both phases are currently deterministic (rule-based dedup / summarization). Comments mark them as "Phase C will swap this for an LLM call." Until LLM versions land, env-flag is the fastest way to A/B test the deterministic versions in production without paying token cost when disabled.

### `MirrorEngine` and the bus

Earlier versions of `MirrorEngine::start` required `Arc<DomainEventBus>` because some sources subscribed directly. That coupling was removed; sources now receive signals through the `SignalConsumer` path. The bus is still plumbed to `run_reforge` (Phase 6.5 community events) — but mirror itself doesn't need it.

### Petgraph is the only graph library

Both Louvain (undirected, `UnGraph<String, f64>`) and PPR (directed, `DiGraph<String, f32, u32>`) use petgraph. The intentional `u32` node-index cap on the PPR digraph trades node-count ceiling for memory efficiency.

### Strategy file layout

Strategy files live in `~/.klyntbot/skills/<skill-name>/` directories (NOT `~/.klyntbot/strategy/` as the overview's storage tree implied — to be corrected). Each directory contains:
- `SKILL.md` — the main skill file (frontmatter + body)
- `references/*.md` — reference materials loaded on demand
- `scripts/*.md` — sometimes used for executable templates

The `SkillFileManager` root is passed in at construction time; not hard-coded.

### `strategy_records` table is raw-SQL accessed

`reforge/feedback.rs:173` reads from `strategy_records` via a raw SQL query rather than a typed repo struct. The table stores runtime signal summaries between reforge runs. **Not wired through `Repos`** — easy to miss when surveying repo coverage.

### KCA validation gates

`./scripts/run_kca_validation.sh` enforces quality / perf / stability gates. Soak test runs only on tagged release branches (`RUN_SOAK=1`). See [`subsystems/14-validation.md`](./14-validation.md) for the per-gate breakdown.

### Adding a feature to the AI signal pipeline

1. In your feature crate, define an event enum: `#[derive(AiEvent)] enum MyFeatureEvent { ... }` with per-variant `salience`, `importance`, `entity`, optional `metric`.
2. Define an entity struct: `#[derive(AiEntity)] struct MyThing { ... }` with `#[ai(entity_type = "...", embed_on = [...])]`.
3. Define a feature marker: `#[derive(AiFeature)] struct MyFeature; impl AiFeature { ... }` with `recall_domain`, `skill`, `event`, etc.
4. Publish events: `domain_bus.publish(DomainEvent::MyFeatureSomethingHappened { ... })` — your enum's `Into<DomainEvent>` impl handles routing.
5. The `SignalRouter` (constructed in `app-core::init`) picks up automatically once your feature is registered in `AiFeatureRegistry`.

### Adding a reforge hook

1. Pick an existing trait (`CodingPhaseRunner`, `GraphEnrichmentHandler`, etc.) or add a new one in `cognitive/services/reforge/mod.rs`.
2. Implement in `app-core` (avoids circular dep).
3. Pass to `run_reforge` as `Some(&handler)`.
4. The cycle degrades gracefully when `None`.

### Adding a mirror signal source

1. Create `crates/cognitive/src/mirror/sources/my_source.rs` implementing `MirrorSignalSource`.
2. Register in `MirrorEngine::start` — either unconditionally or behind `Option<&Repo>` parameters.
3. Implement signal accumulation + flush. Flushes get their own tokio task; handle is returned in `StartedMirror.flush_handles`.

### Adding a new `RecallDomain` variant

1. Add the variant to `RecallDomain` enum in `crates/ai-core/src/recall_domain.rs`.
2. Update `RecallProviderRegistry` consumers in `cognitive` and `app-core`.
3. New variants are forward-compatible (no schema migration needed).
