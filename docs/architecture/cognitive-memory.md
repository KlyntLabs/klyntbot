# Cognitive Memory System

## Overview

The cognitive memory system (`crates/cognitive/`) provides persistent, evolving knowledge about the user. It processes domain events from the agent runtime, extracts semantic facts, consolidates them with existing knowledge, and makes memories available for retrieval during conversations.

The system is inspired by cognitive science models: facts decay over time following spaced-repetition curves, can be superseded by newer information, and are scored by a multi-factor relevance formula during retrieval.

**Key files:**
- `crates/cognitive/src/types.rs` -- Core types: `SemanticFact`, `EpisodicMemory`, `ProceduralRule`, `UserModel`, `MemoryOp`
- `crates/cognitive/src/background.rs` -- `BackgroundConsolidationService`, salience evaluation, event routing
- `crates/cognitive/src/decay.rs` -- FSRS retrievability formula, 5-factor relevance scoring
- `crates/cognitive/src/repos/` -- SQLite repositories with FTS5 search
- `crates/cognitive/src/extraction.rs` -- Fact extraction from observations
- `crates/cognitive/src/consolidation.rs` -- Merge/supersede/add decisions
- `crates/storage/src/vector_store.rs` -- LanceDB vector search for cognitive facts

## Memory Types

### Semantic facts (bi-temporal, FSRS)

The primary memory type. A semantic fact is a structured triple (subject, predicate, object) with metadata:

```rust
pub struct SemanticFact {
    pub id: String,
    pub domain: String,        // "identity", "energy", "work", "finance", etc.
    pub subject: String,       // e.g., "user"
    pub predicate: String,     // e.g., "peak_hours"
    pub object: String,        // e.g., "10am-12pm"
    pub confidence: f64,       // 0.0-1.0
    pub source: String,        // "observed", "stated", "inferred"

    // Bi-temporal markers
    pub valid_from: String,        // When the fact became true
    pub valid_until: Option<String>, // When it stopped being true
    pub recorded_at: String,       // When we learned it
    pub superseded_at: Option<String>,  // When a newer fact replaced it
    pub superseded_by: Option<String>,  // ID of the replacing fact

    // FSRS decay
    pub stability: f64,          // Spaced-repetition stability parameter
    pub last_accessed: Option<String>,
    pub access_count: i64,

    pub project_id: Option<String>,
    pub memory_type: String,     // Default: "fact"
}
```

**Bi-temporal design**: Facts track two time dimensions -- *valid time* (when the fact was true in the real world) and *transaction time* (when we recorded it). This allows the system to answer "what did we know at time T?" and "what was true at time T?" independently. Superseded facts are preserved with `superseded_at`/`superseded_by` markers rather than deleted.

### Episodic memories

Records of specific events with importance scoring:

```rust
pub struct EpisodicMemory {
    pub id: String,
    pub domain: String,
    pub content: String,
    pub summary: Option<String>,
    pub importance: f64,     // 0.0-1.0
    pub occurred_at: String,
    pub recorded_at: String,
    pub stability: f64,
    pub last_accessed: Option<String>,
    pub access_count: i64,
    pub project_id: Option<String>,
}
```

Episodic memories are created automatically from high-importance observations (importance >= 0.7) during background consolidation. They capture "what happened" rather than enduring facts.

### Procedural rules

Learned behavioral rules from reflection:

```rust
pub struct ProceduralRule {
    pub id: String,
    pub domain: String,       // "productivity", "tasks", "finance", "coaching", "general"
    pub rule_text: String,    // Natural language rule
    pub confidence: f64,
    pub source: String,
    pub signal_count: i64,    // How many signals support this rule
    pub created_at: String,
    pub updated_at: String,
    pub active: bool,
    pub project_id: Option<String>,
}
```

Procedural rules encode patterns like "User is most productive between 9-11am" or "User prefers concise responses." They are generated by the reflection system from accumulated observations.

## Background Consolidation

The `BackgroundConsolidationService` runs as a tokio task, subscribing to the `DomainEventBus` and processing events through a three-stage pipeline.

### Pipeline: DomainEvent -> salience evaluation -> route

Each incoming `DomainEvent` is evaluated for salience, producing one of three verdicts:

| Verdict | Action | Example Events |
|---------|--------|----------------|
| `Extract` | Immediate extraction + consolidation | `UserStatedFact`, `ChatTurnCompleted`, `BudgetAlert`, `UserCorrectedAI` |
| `Accumulate` | Buffer until pattern threshold reached | `ProductivityScoreComputed`, `TaskCompleted`, `DistractionDetected`, `FocusSessionEnded` |
| `Discard` | Silently dropped | Low-value events like `SessionCreated`, `RuleEvolved` |

### Extract path (hot path)

1. Convert `DomainEvent` to an `Observation` (domain, content, importance, source)
2. Call `extract_from_observation()` to produce `ExtractedFact` triples via the `ExtractionHandler`
3. Call `consolidate_batch()` to merge extracted facts with existing knowledge, producing `MemoryOp` results (Add, Update, Delete, Noop)
4. If the observation has importance >= 0.7, store it as an `EpisodicMemory`
5. Emit `PipelineEvent::Extraction` and `PipelineEvent::Consolidation` for the debug dashboard

### Accumulate path

1. Convert `DomainEvent` to an `Observation`
2. Persist the observation via `AccumulatedObservationRepo` (survives restarts)
3. Add to in-memory `AccumulatedEntry` keyed by event type
4. Track unique days seen and total observation count
5. When the entry reaches the promotion threshold (configurable `promote_threshold` events across `min_days` unique days):
   - Summarize all accumulated observations into a single observation
   - Run it through the extract path (extraction + consolidation)
   - Clear the accumulated entries (both in-memory and persisted)

### Event to observation mapping

Events are mapped to observations with domain assignment and importance scoring:

| Event | Domain | Importance |
|-------|--------|------------|
| `UserStatedFact` | (from event) | 1.0 |
| `UserCorrectedAI` | meta | 1.0 |
| `ChatTurnCompleted` | general | 0.8 |
| `BudgetAlert` | finance | 0.9 |
| `CoachingFeedback` | coaching | 0.9 |
| `NarrativeGenerated` | productivity | 0.7 |
| `TransactionRecorded` | finance | 0.4 (0.8 if over budget) |
| `ProductivityScoreComputed` | productivity | 0.5 |
| `TaskCompleted` | tasks | 0.5 |
| `DistractionDetected` | productivity | 0.6 |
| `FocusSessionEnded` | productivity | 0.5 |

## FSRS Decay Model

### Retrievability formula

The system uses an FSRS-inspired (Free Spaced Repetition Scheduler) formula for memory decay:

```
R = exp(ln(0.9) * elapsed_days / stability)
```

Where:
- `R` is the retrievability (probability of successful recall, 0.0-1.0)
- `elapsed_days` is the time since last access
- `stability` is the FSRS stability parameter (in days)

At `elapsed_days == stability`, retrievability is exactly 0.9 (90% recall probability). As elapsed time grows beyond stability, recall probability drops exponentially.

### Stability updates

When a fact is accessed (retrieved and used):
- **Successful retrieval**: `new_stability = min(current + max(ln(1 + current), 0.1), max_stability)`
- **Failed retrieval**: Stability unchanged

The logarithmic growth ensures diminishing returns -- frequently accessed facts gain stability quickly at first, then plateau. The `max_stability` cap (default: 30 days) prevents any single fact from dominating retrieval rankings indefinitely.

### 5-factor relevance scoring

Memory retrieval ranking uses a weighted combination of five signals:

| Factor | Default Weight | Description |
|--------|---------------|-------------|
| Semantic similarity | 0.30 | Vector cosine similarity between query and fact embedding |
| Retrievability | 0.20 | FSRS decay probability (how "fresh" the memory is) |
| Importance | 0.15 | Source importance (user-stated facts = 1.0, inferred = lower) |
| Access frequency | 0.10 | Normalized access count |
| Situational boost | 0.25 | Context-dependent boost (matching domain, active project, etc.) |

The formula:

```
score = clamp(semantic * 0.3 + retrievability * 0.2 + importance * 0.15 + frequency * 0.1 + situation * 0.25, 0.0, 1.0)
```

Weights are configurable via `RelevanceWeights`.

## Search

### FTS5 full-text search

Semantic facts are indexed in an FTS5 virtual table (`semantic_facts_fts`) for BM25-ranked keyword search:

```rust
pub async fn search_fts(
    &self,
    query: &str,
    domain: Option<&str>,
    limit: usize,
) -> Result<Vec<SemanticFact>, sqlx::Error>
```

FTS5 search supports:
- Free-text queries across subject, predicate, and object fields
- Optional domain filtering
- BM25 ranking via `fts.rank`
- Exclusion of superseded facts

### Vector similarity search

Cognitive fact embeddings are stored in LanceDB (`cognitive_fact_embeddings` table) with 384-dimensional vectors. The `VectorStore::search_cognitive_facts()` method provides:

- Nearest-neighbor search with cosine distance
- Domain filtering via SQL predicates (`domain IN (...)`)
- Configurable `top_k` and `min_similarity` threshold
- Score computed as `1.0 - distance` (cosine similarity)

### Hybrid search

The retrieval system combines both search modalities:
1. FTS5 for keyword recall (BM25 ranking)
2. Vector search for semantic similarity
3. Results merged and re-ranked by the 5-factor relevance formula

## User Model

The `UserModel` aggregates active semantic facts across 10 domains into a structured view:

```rust
pub struct UserModel {
    pub identity: Vec<SemanticFact>,     // Name, age, location, etc.
    pub energy: Vec<SemanticFact>,       // Energy patterns, sleep, circadian
    pub work: Vec<SemanticFact>,         // Job, projects, work habits
    pub finance: Vec<SemanticFact>,      // Financial goals, budgets
    pub learning: Vec<SemanticFact>,     // Learning goals, skill levels
    pub preferences: Vec<SemanticFact>,  // Communication style, UI prefs
    pub other: Vec<SemanticFact>,        // general, tasks, coaching, meta
}
```

### 10 domains

The user model spans these domains, defined in `USER_MODEL_DOMAINS`:

1. `identity` -- Personal identity facts
2. `energy` -- Energy and productivity patterns
3. `work` -- Work context and habits
4. `finance` -- Financial knowledge
5. `learning` -- Learning goals and progress
6. `preferences` -- User preferences
7. `general` -- General facts
8. `tasks` -- Task-related knowledge
9. `coaching` -- Coaching interaction patterns
10. `meta` -- Meta-knowledge (corrections, system behavior)

### Building the user model

`load_user_model()` iterates over all 10 domains, calls `list_active(domain)` on the `SemanticFactRepo`, and assigns facts to the appropriate `UserModel` field. Domains not covered by named fields (`general`, `tasks`, `coaching`, `meta`) are collected into `other`.

## Data Lifecycle

### Recording

Facts enter the system through two paths:
1. **Background consolidation**: Domain events are processed by the `BackgroundConsolidationService`, which extracts facts and consolidates them against existing knowledge.
2. **Direct insertion**: The `SemanticFactRepo::upsert()` method supports INSERT or UPDATE via `ON CONFLICT DO UPDATE`.

### Supersession

When a new fact contradicts or updates an existing one (same subject + predicate):

1. The consolidation handler identifies the conflict via `find_similar(subject, predicate)`
2. The old fact is superseded: `superseded_at` is set to the current timestamp and `superseded_by` is set to the new fact's ID
3. The new fact is inserted with its own `valid_from` timestamp
4. The old fact remains in the database but is excluded from active queries (filtered by `superseded_at IS NULL`)

### Archival

Superseded facts older than a configurable threshold are moved to an archive table (`semantic_facts_archive`):

```rust
pub async fn archive_superseded(&self, older_than_days: i64) -> Result<u64, sqlx::Error>
```

This operation:
1. Copies qualifying superseded facts to `semantic_facts_archive`
2. Deletes them from `semantic_facts`
3. Runs in a transaction for atomicity

Archived facts can be:
- Searched by domain and keyword via `search_archived()`
- Counted via `count_archived()`
- Reinstated to the active table via `reinstate_archived()`, which clears `superseded_at`, `superseded_by`, and `valid_until`

### Compaction

Facts with low stability (retrievability below a threshold) are candidates for compaction. The `list_low_stability(max_stability)` method identifies these facts for review or cleanup by the reflection system.

### Access tracking

When a fact is retrieved and used in a conversation:

1. `record_access(id, new_stability)` increments `access_count`, updates `last_accessed`, and sets the new stability value
2. The stability increase follows the FSRS update formula (logarithmic growth, capped at `max_stability`)
3. Higher stability means slower decay, so frequently-used facts persist longer
