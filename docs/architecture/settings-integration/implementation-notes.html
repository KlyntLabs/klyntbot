Settings Integration — Implementation Notes

Running log of design decisions, deviations, tradeoffs, and open questions while implementing 05-integration-plan.md.

Pre-implementation Findings (2026-05-21)

  • Deviation Linter mismatch: CLAUDE.md says "ESLint via bun run lint", but desktop-ui/package.json uses biome check .. We follow the actual build scripts (Biome) rather than the docs.
  • Decision Test runner: The plan says bun run test useConfigSection, but Vitest does not accept positional file filters this way. We use bun run test -- useConfigSection (Vitest's filter syntax).
  • Decision Import aliases: The plan uses @/api/client for invoke. The project already has this alias mapped in vite.config.ts and tsconfig.json. Verified working.
  • Open Binding regeneration: Phase 0 does not add new backend commands, so bindings.ts does not need regeneration yet. We will run cargo tauri dev when we add new commands in Phase P (Soul/Persona).

Phase 0 — Foundation (Done)

Task 0.1: useConfigSection

  • Decision Kept the setValue in the return tuple (not in the plan's initial sketch but present in the canonical pattern) so callers can do optimistic local edits if needed.

Task 0.2: Reusable field components

  • Decision Tailwind colors: The tracing module defines --color-accent inside .tracing-root, so bg-accent is not available in the settings context. We use explicit bg-[var(--border-accent)] and other CSS custom-property arbitrary values instead. This keeps components theme-aware without adding global Tailwind theme configuration.
  • Deviation The plan's ToggleField sketch used bg-accent and bg-neutral-500/40. We replaced these with bg-[var(--border-accent)] and bg-[var(--surface-control-disabled)] to match the app's actual token system.
  • Decision SliderField onBlur: Added an optional onBlur prop to SliderField so it can participate in the save-on-blur pattern alongside TextField and NumberField.

Task 0.3: Domain registry + SettingsShell

  • Decision Registry file uses .tsx extension because it exports JSX icon elements (<Brain aria-hidden />). The plan assumed .ts but TS requires .tsx for JSX syntax.

Task 0.4: Mount shell behind flag

  • Decision Used a localStorage flag (klynt-new-settings) rather than a UI tab or route. This is zero-UI-regression: end users see nothing different unless they explicitly set the flag in DevTools. The new shell swaps in place of the old SettingsView when the flag is active, reusing the same modal infrastructure.
  • Deviation Plan says "temporary route/tab"; we used a localStorage gate + lazy conditional component swap in MainApp.tsx because the app does not have a traditional router and this avoids touching the old SettingsNav / SettingsSectionContainers at all.

Phase 1 — Vertical slice: Models & Providers (Done)

Task 1.1: TS types

  • Decision Types in configSectionTypes.ts mirror the full Rust structs (including nested execution, extendedThinking, etc.) rather than the plan's abbreviated sketches. This gives us headroom for future phases without retyping.

Task 1.2: SettingsModelsSection

  • Deviation The plan specifies a SelectField for model with options from model_list. We used a TextField for model instead because model_list requires a workspaceId and the settings context may not have one loaded. A free-text model ID is also more accurate to the schema (which is String, not an enum). We can upgrade to a SelectField later if we add a workspace-agnostic model catalog command.
  • Decision API-key entry uses SecretField with a "Configured" badge. We never render the raw key value (the backend redacts it in Secret debug output anyway). Entering a new key overwrites the old one; leaving blank sends null to clear it.
  • Tradeoff Save granularity: We save the entire defaults object on every blur, merging with the current config server-side. The backend's config_update_section does a deep merge, so sending a partial { defaults: { temperature: 0.5 } } is safe and does not wipe other defaults.

Task 1.3: Register domain

  • Done Added Models & Providers to settingsDomains with the Brain icon. It renders in the new shell nav when the dev flag is enabled.

Phase 2 — Vertical slice: App & UI (Done)

Task 2.1: Rust schema — UiConfig

  • Decision Created crates/config/src/schema/ui.rs with UiConfig struct containing 14 fields migrated from the dead AppSettings stack: theme, uiScale, uiFontFamily, codeFontFamily, codeFontSize, notification toggles, threadTitleAutogenerationEnabled, automaticAppUpdateChecksEnabled, chatHistoryScrollbackItems, showMessageFilePath, splitChatDiffView, usageShowRemaining.
  • Decision chatHistoryScrollbackItems is Option<u32> with default Some(100) so that null can represent "unlimited" in future UI iterations, matching the old AppSettings semantics.
  • Decision No specta::Type derive on UiConfig because we only access it via generic config_get_section / config_update_section (which work with serde_json::Value), not via new Tauri commands. This keeps the Rust side minimal.

Task 2.2: TypeScript types + section component

  • Decision Added UiConfig to configSectionTypes.ts with all fields optional, matching the deep-merge-safe pattern used by AgentsConfig and ProvidersConfig.
  • Decision SettingsAppSection groups fields into four cards: Appearance, Notifications, Display, Behaviour. This replaces both the old "App" and "Display" settings tabs without changing the underlying data model.
  • Tradeoff Toggles and selects save immediately; sliders, text fields, and number fields save on blur. This is the same interaction model as Phase 1 and avoids excessive IPC chatter for high-frequency inputs like uiScale.
  • Deviation chatHistoryScrollbackItems is rendered as a plain NumberField without an "Unlimited" toggle. The old UI had a checkbox that set the value to null; we deferred that complexity to Phase D when we fully replace the old Display section.

Task 2.3: Register domain

  • Done Added App & UI domain (id "ui") to settingsDomains with Monitor icon, placed before Models & Providers in the nav list.

Simplify Review & Fixes (Post-Phase 2)

Issues found and fixed

  • Fixed FieldLayout extraction: Created FieldLayout component to DRY the repeated label/description wrapper across TextField, NumberField, SelectField, SliderField, and SecretField. Each field component now only supplies its unique input element.
  • Fixed Single draft state: Refactored SettingsAppSection from 15 individual useState hooks to one draft: UiConfig state object, initialized once from the loaded config. Eliminates the redundant cascade of setters after every successful patch.
  • Fixed No-op guard + generation tracking in useConfigSection: Added patch-generation counter so only the most recent patch result updates state (prevents stale overwrites). Added no-op guard that skips the RPC when the patch value equals the current value. Added patching state for UI feedback and proper error handling for patch failures.
  • Fixed Error state rendering: Both SettingsAppSection and SettingsModelsSection now render the error returned by useConfigSection instead of hanging indefinitely on "Loading…".
  • Fixed Strongly-typed theme: Changed theme from string to ThemePreference union ("system" | "light" | "dark" | "dim") in TypeScript, matching the Rust documentation and old AppSettings type.
  • Fixed Unnecessary comments: Removed {/* Nav */} and {/* Content */} comments from SettingsShell.tsx.

Issues noted but skipped (intentional design)

  • Skipped Duplicate of existing SettingsView/SettingsDisplaySection: The new shell and app section intentionally replace the old stack. The old code will be deleted in Phase D. Reusing old CSS-class-based primitives would couple the new system to the deprecated stack.
  • Skipped useConfigSection vs useTauriQuery: The new hook is deliberately lightweight (no react-query cache/invalidation) because the new settings UI is the only consumer of these config sections and we want to avoid coupling to the legacy query key system.
  • Skipped Provider name list duplication: Minor; the existing PROVIDER_DISPLAY_NAMES map is in a different feature module and lacks some providers. Centralizing can be done later.
