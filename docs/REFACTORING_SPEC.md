### 1.3 Agent Iteration Loop (3 nearly-identical loops)

The core agent iteration loop is duplicated across three methods:

| Method | Lines | Unique behavior |
|---|---|---|
| `process_message()` | 241-312 | Non-streaming, publishes to bus |
| `process_system_message()` | 412-487 | Non-streaming, routes to origin channel |
| `process_direct()` | 569-750 | Streaming + non-streaming, returns String |

**Refactored:** Extract the common iteration logic into a single method:

```rust
/// Result of running the agent iteration loop.
struct AgentIterationResult {
    content: String,
}

/// Run the agent iteration loop with the given messages.
/// Returns the final response content.
async fn run_agent_loop(
    &self,
    messages: Vec<Message>,
    use_streaming: bool,
) -> Result<String> {
    let max_iterations = self.config.agents.defaults.max_tool_iterations as usize;
    let mut current_messages = messages;
    let mut final_content = None;

    for iteration in 0..max_iterations {
        debug!("Agent iteration {}/{}", iteration + 1, max_iterations);

        let tool_registry = self.tool_registry.read().await;
        let tools = tool_registry.get_definitions();
        drop(tool_registry);

        // Delegate to streaming or non-streaming path
        let response = if use_streaming && self.provider.supports_streaming() {
            self.run_streaming_iteration(&mut current_messages, &tools).await?
        } else {
            self.run_standard_iteration(&mut current_messages, &tools).await?
        };

        match response {
            IterationOutcome::ToolCallsProcessed => continue,
            IterationOutcome::FinalContent(content) => {
                final_content = Some(content);
                break;
            }
            IterationOutcome::Empty => {
                warn!("LLM returned no content and no tool calls");
                break;
            }
        }
    }

    Ok(final_content.unwrap_or_else(|| {
        "I've finished processing. Is there anything else I can help with?".to_string()
    }))
}

enum IterationOutcome {
    ToolCallsProcessed,
    FinalContent(String),
    Empty,
}
```

Then `process_message()`, `process_system_message()`, and `process_direct()` each become ~30 lines: prepare messages, call `run_agent_loop()`, save session, send response.

## 3. Channel Manager Consolidation

**Priority: MEDIUM**
**File: `src/channels/manager.rs` (217 lines)**

### 3.1 Repeated Channel Initialization Blocks

`initialize_channels()` (lines 34-100) contains 6 repetitive blocks:

```rust
if self.config.channels.telegram.enabled {
    info!("Initializing Telegram channel");
    // ... specific creation logic
    match TelegramChannel::new(self.config.channels.telegram.clone(), groq_key) {
        Ok(channel) => {
            channels.insert("telegram".to_string(), Arc::new(channel));
        }
        Err(e) => error!("Failed to create Telegram channel: {}", e),
    }
}
```

**Refactored approach:** Use a helper macro or function to reduce repetition. Since each channel has different constructors (Telegram takes `groq_key`, WhatsApp doesn't return Result), a macro is more appropriate:

```rust
macro_rules! init_channel {
    ($channels:expr, $config:expr, $name:literal, $create:expr) => {
        if $config.enabled {
            info!("Initializing {} channel", $name);
            match $create {
                Ok(channel) => {
                    $channels.insert($name.to_string(), Arc::new(channel) as DynChannel);
                }
                Err(e) => error!("Failed to create {} channel: {}", $name, e),
            }
        }
    };
}

pub async fn initialize_channels(&self) -> Result<()> {
    let mut channels = self.channels.write().await;

    // Telegram (needs groq key for voice transcription)
    let groq_key = (!self.config.providers.groq.api_key.is_empty())
        .then(|| self.config.providers.groq.api_key.clone());
    init_channel!(channels, self.config.channels.telegram, "telegram",
        TelegramChannel::new(self.config.channels.telegram.clone(), groq_key));

    init_channel!(channels, self.config.channels.discord, "discord",
        DiscordChannel::new(self.config.channels.discord.clone()));

    // WhatsApp doesn't return Result, so handle separately:
    if self.config.channels.whatsapp.enabled {
        info!("Initializing WhatsApp channel");
        let channel = WhatsAppChannel::new(self.config.channels.whatsapp.clone());
        channels.insert("whatsapp".to_string(), Arc::new(channel));
    }

    init_channel!(channels, self.config.channels.qq, "qq",
        QQChannel::new(self.config.channels.qq.clone()));

    init_channel!(channels, self.config.channels.slack, "slack",
        SlackChannel::new(self.config.channels.slack.clone()));

    init_channel!(channels, self.config.channels.email, "email",
        EmailChannel::new(self.config.channels.email.clone()));

    Ok(())
}
```

## 5. Error Handling Consistency

**Priority: HIGH**

### 5.1 Tools Returning `Ok("Error: ...")` Instead of `Err(...)`

Multiple tools return success with error-formatted strings instead of actual errors. This masks failures from the calling code.

**Affected locations:**

| File | Lines | Pattern |
|---|---|---|
| `filesystem.rs` (ReadFileTool) | 81 | `Ok(format!("Error: File not found: {}", path))` |
| `filesystem.rs` (ReadFileTool) | 85 | `Ok(format!("Error: Not a file: {}", path))` |
| `filesystem.rs` (ReadFileTool) | 90 | `Ok(format!("Error reading file: {}", e))` |
| `filesystem.rs` (WriteFileTool) | ~161 | `Ok(format!("Error: ..."))` patterns |
| `filesystem.rs` (EditFileTool) | ~229, 237-239 | `Ok(format!("Error: ..."))` patterns |
| `shell.rs` (ExecTool) | ~166, 232-233 | `Ok(format!("Error: ..."))` patterns |
| `web.rs` | Various | `Ok(format!("Error: ..."))` patterns |

**Important context:** In the agent loop (e.g., `agent_loop.rs:290-293`), tool errors are caught and formatted:
```rust
let result_str = match result {
    Ok(r) => r,
    Err(e) => format!("Error: {}", e),
};
```

This means the LLM sees `"Error: ..."` either way. However, the tools should still return proper `Err` variants for:
1. Correct error propagation if tools are ever called outside the agent loop
2. Metrics and logging that distinguish success from failure
3. Consistent API contract

**Refactored approach for `ReadFileTool::execute()`:**

```rust
async fn execute(&self, args: Value) -> Result<String> {
    let path = args
        .get("path")
        .and_then(|v| v.as_str())
        .ok_or_else(|| ToolError::InvalidParams("missing 'path' parameter".to_string()))?;

    let file_path = self.base.resolve_path(path)?;

    if !file_path.exists() {
        return Err(ToolError::ExecutionFailed(format!("File not found: {}", path)).into());
    }

    if !file_path.is_file() {
        return Err(ToolError::ExecutionFailed(format!("Not a file: {}", path)).into());
    }

    fs::read_to_string(&file_path)
        .await
        .map_err(|e| ToolError::ExecutionFailed(format!("Error reading file: {}", e)).into())
}
```

Apply the same pattern to **all tool `execute()` methods** in `filesystem.rs`, `shell.rs`, and `web.rs`.

## 7. Performance Optimizations

**Priority: MEDIUM**

### 7.1 Excessive Cloning in Session Save

**File: `agent_loop.rs`, lines 325, 499, 761**

```rust
let session_clone = session.clone();
if let Err(e) = session_manager.save(&session_clone) { ... }
```

The `session.clone()` is done because `session` is a `&mut Session` borrow from `get_or_create()`, and `save()` takes `&Session`. The clone is needed due to the mutable borrow. **This is a necessary clone given the current API.**

**Improvement:** Change `SessionManager::save()` to accept `&str` (session key) and save internally, eliminating the need for the caller to clone:

```rust
// In src/session/manager.rs, change:
pub fn save(&self, session: &Session) -> Result<()> { ... }

// To:
pub fn save_by_key(&mut self, key: &str) -> Result<()> {
    if let Some(session) = self.sessions.get(key) {
        // save the session directly from internal storage
        self.persist(session)?;
    }
    Ok(())
}
```

Then in agent_loop.rs:
```rust
let mut session_manager = self.session_manager.write().await;
if let Ok(session) = session_manager.get_or_create(&session_key) {
    session.add_message("assistant", &response_content);
}
session_manager.save_by_key(&session_key)?;
```

### 7.2 RwLock Held During LLM Calls

**Not an issue.** The tool_registry and context_builder RwLock are correctly `drop()`-ed before the LLM call at lines 247/574 of `agent_loop.rs`. The session_manager lock is also dropped at line 218/555 before the LLM call. No lock is held during LLM I/O.

### 7.3 Web Tools Creating Individual reqwest::Clients

**File: `src/tools/web.rs`**

Both `WebSearchTool` and `WebFetchTool` create their own `reqwest::Client` instances. Each client maintains its own connection pool and TLS state.

**Refactored:** Share a single `reqwest::Client` by passing it during construction:

```rust
pub struct WebSearchTool {
    client: Client,
    brave_api_key: Option<String>,
    max_results: u8,
}

impl WebSearchTool {
    pub fn new(client: Client, brave_api_key: Option<String>, max_results: u8) -> Self {
        Self { client, brave_api_key, max_results }
    }
}
```

Create the shared client in `AgentLoop::new_with_cron()` and pass it to both web tools.

### 7.4 Tokio "full" Features

**File: `Cargo.toml`**

```toml
tokio = { version = "1", features = ["full"] }
```

This compiles all tokio features including `test-util`, `signal`, `process`, `fs`, etc. **Replace with specific features:**

## 9. Cross-Cutting Patterns

### 9.1 Tool Context Injection Pattern

**Files: `message.rs`, `spawn.rs`, `cron_tool.rs`**

All three tools use `Arc<RwLock<(String, String)>>` for channel/chat_id context:

```rust
// message.rs
pub struct MessageTool {
    outbound_tx: mpsc::Sender<OutboundMessage>,
    context: Arc<RwLock<(String, String)>>,
}

// spawn.rs
pub struct SpawnTool {
    context: Arc<RwLock<(String, String)>>,
    // ...
}

// cron_tool.rs
pub struct CronTool {
    context: Arc<RwLock<(String, String)>>,
    // ...
}
```

And `update_tool_contexts()` in `agent_loop.rs:522-537` individually updates each:

```rust
if let Some(tool) = registry.get("message") { tool.set_context(channel, chat_id); }
if let Some(tool) = registry.get("spawn") { tool.set_context(channel, chat_id); }
if let Some(tool) = registry.get("cron") { tool.set_context(channel, chat_id); }
```

**Refactored:** Extract a shared `ToolContext` type:

```rust
// In src/tools/mod.rs:
use std::sync::Arc;
use tokio::sync::RwLock;

/// Shared context for tools that need routing information.
#[derive(Clone)]
pub struct ToolContext {
    inner: Arc<RwLock<(String, String)>>,
}

impl ToolContext {
    pub fn new() -> Self {
        Self {
            inner: Arc::new(RwLock::new((String::new(), String::new()))),
        }
    }

    pub async fn set(&self, channel: &str, chat_id: &str) {
        let mut ctx = self.inner.write().await;
        ctx.0 = channel.to_string();
        ctx.1 = chat_id.to_string();
    }

    pub async fn get(&self) -> (String, String) {
        self.inner.read().await.clone()
    }
}
```

Then share a single `ToolContext` instance across all context-aware tools:

```rust
// In AgentLoop::new_with_cron():
let tool_context = ToolContext::new();
tool_registry.register(MessageTool::new(bus.outbound_sender(), tool_context.clone()));
tool_registry.register(SpawnTool::with_manager(subagent_manager.clone(), tool_context.clone()));
tool_registry.register(CronTool::with_service(cron_svc, tool_context.clone()));
```

And simplify `update_tool_contexts()`:
```rust
async fn update_tool_contexts(&self, channel: &str, chat_id: &str) {
    self.tool_context.set(channel, chat_id).await;
}
```

This eliminates the need for the `set_context()` method on the `Tool` trait entirely, and removes the per-tool RwLock overhead.

### 9.2 Reconnection Loop Pattern in Channels

Discord (`discord.rs:503-511`), WhatsApp (`whatsapp.rs:175-183`), Slack (`slack.rs:399-407`), and QQ (`qq.rs:345-353`) all use the same reconnection pattern:

```rust
while *self.running.read().await {
    if let Err(e) = self.xxx_loop(bus.clone()).await {
        error!("XXX error: {}", e);
        if *self.running.read().await {
            info!("Reconnecting to XXX in 5 seconds...");
            sleep(Duration::from_secs(5)).await;
        }
    }
}
```

**This is 4 nearly identical blocks.** Consider a helper:

```rust
// In src/channels/mod.rs:
pub async fn reconnect_loop<F, Fut>(
    name: &str,
    running: &Arc<RwLock<bool>>,
    mut connect: F,
) where
    F: FnMut() -> Fut,
    Fut: std::future::Future<Output = Result<()>>,
{
    while *running.read().await {
        if let Err(e) = connect().await {
            error!("{} error: {}", name, e);
            if *running.read().await {
                info!("Reconnecting to {} in 5 seconds...", name);
                sleep(Duration::from_secs(5)).await;
            }
        }
    }
}
```

Then each channel's `start()` becomes:
```rust
async fn start(&self, bus: Arc<MessageBus>) -> Result<()> {
    *self.running.write().await = true;
    reconnect_loop("Discord", &self.running, || self.gateway_loop(bus.clone())).await;
    // cleanup...
    Ok(())
}
```

### 9.3 Wizard Provider Config Match Arm Duplication

**File: `src/cli/wizard.rs`, lines 84-106**

```rust
match provider.key {
    "anthropic" => {
        config.providers.anthropic.api_key = api_key;
        config.agents.defaults.model = model;
    }
    "openai" => {
        config.providers.openai.api_key = api_key;
        config.agents.defaults.model = model;
    }
    // ... 3 more identical arms
}
```

Each arm does the same thing: set `api_key` and `model`. The only difference is which provider field to access.

**Refactored:** Add a method to `Config`:

```rust
impl Config {
    /// Set the API key for a provider by name.
    pub fn set_provider_key(&mut self, provider_name: &str, key: String) {
        match provider_name {
            "anthropic" => self.providers.anthropic.api_key = key,
            "openai" => self.providers.openai.api_key = key,
            "deepseek" => self.providers.deepseek.api_key = key,
            "gemini" => self.providers.gemini.api_key = key,
            "openrouter" => self.providers.openrouter.api_key = key,
            _ => {}
        }
    }
}
```

Then the wizard becomes:
```rust
config.set_provider_key(provider.key, api_key);
config.agents.defaults.model = model;
```
