# Tool context projection: narrow per-tool views over `RoutingContext`

Every tool received the full 23-field `RoutingContext` by reference, regardless of need. 18 of 42 tools used none of it (`_ctx`); filesystem tools used exactly one field (`hook_engine`); only `bash`, `ask_user`, and `subagents` were genuinely wide. The struct's interface was as wide as its implementation — shallow — and it grew unbounded (fields tagged "Phase 2.3a" mark the accretion). The consequences: no leak prevention (any tool could reach any other tool's wiring), and an accidentally-shallow test surface — a newly added field defaulted to `None` in every existing test with no compile error forcing anyone to consider it.

We decided to **project `RoutingContext` into narrow, borrowed context views** at the `#[derive(Tool)]` bridge. A tool declares the slice it needs via a GAT associated type `type Ctx<'a>: FromRoutingContext<'a>` on `ToolExecute`; the bridge constructs that view from the full context before calling the tool. The untyped `Tool::execute(args, &RoutingContext)` boundary is unchanged — the `ToolRegistry` still dispatches one signature for all tools — so the change is confined to the typed side authored by tool writers.

We chose a **tiered superset ladder** (`() ⊂ HookCtx ⊂ IoCtx ⊂ FullCtx`) over composable per-concern views (tuples) or bespoke per-tool structs. The ladder keeps the number of distinct types small (a tool picks the smallest rung that fits) while still making each tool's dependency surface explicit.

`HookCtx` and `IoCtx` **own cheap clones** of the fields they expose (an `Arc` refcount bump for `hook_engine`, small clones for `session_key`/`channel`/`chat_id`/`message_id`, channel-sender clones) rather than borrowing `&RoutingContext`. We first designed them as borrowed views (`Option<&'a T>`) for zero-copy, but that forced edits to every tool body (`.as_ref()`/`.clone()` semantics change for `Option<&T>` vs `Option<T>`). Owning the clones means tool bodies compile **unchanged** — only the `type Ctx` line and the parameter type move — at a per-call cost (a few refcount bumps and small allocs) that is negligible beside the file/shell IO these tools perform. `FullCtx` still borrows (it is just `&RoutingContext` + `Deref`). We deliberately **did not** add a wide `AgentCtx` rung: any rung large enough to serve `bash` + `ask_user` + `subagents` would carry ~20 of 23 fields and narrow nothing. Those few wide tools instead take `FullCtx<'a>` — a `Deref` wrapper over `&RoutingContext` — which is an honest "I need the lot" declaration, no worse than today but explicit at the type level. `FullCtx` doubles as the transitional view that makes the migration always-green.

We kept `#[async_trait]` on `ToolExecute`. We first tried native async-fn-in-trait (to avoid the boxed future), but neither the RPITIT form (`-> impl Future + Send`) nor a plain `async fn` — with elided *or* explicit lifetimes — would accept a GAT-projected borrowed argument (`Self::Ctx<'c>`): every impl failed with E0195 ("lifetime parameters or bounds on method do not match the trait declaration"). `#[async_trait]` elaborates the method's lifetimes and boxes the future, so the GAT becomes an ordinary argument type and trait/impl signatures unify. The per-call box allocation is negligible for tool dispatch (these paths already allocate freely) and is what every other tool in the workspace already pays. `Send` is still enforced — the generated `Tool` bridge is `#[async_trait]` (`Send`) and awaits this future.

We rejected **splitting `RoutingContext` into owned sub-structs** passed through the `Tool` boundary, because the untyped boundary forces a single signature for all tools — sub-structs would still be passed whole, delivering grouping but neither leak prevention nor compile-time test locality. We rejected **accessor traits** (à la the existing `bus::InjectorContext`) for the same reason: a trait the full context implements narrows internal helper calls but not the `execute` boundary or its tests.

Scope covers the two tool families that have a typed layer to project at:

1. **The 12 derive-path tools** that implement `ToolExecute` (all in `klynt-core/src/tools/`: `read, glob, grep, list_dir, write, edit, apply_patch, notebook_edit, plan_mode, bash, web_fetch, tool_search`).
2. **The `#[tool_actions]` family** (`docs, temporal, annotate, mirror, launcher, subagents`). The macro gained an optional `ctx = "View"` attribute: it projects `&RoutingContext` into the named view at the top of the generated `execute` and passes it to every action handler. Absent the attribute, handlers receive `&RoutingContext` as before (backward compatible). The 5 zero-ctx tools declare `ctx = "()"`; `subagents` stays on `&RoutingContext` because it forwards the context to the `SubagentsHandler` dependency-inversion trait (narrowing it would ripple into the `agent` crate) — it is the documented boundary within this family.

**The untyped `Tool` boundary is the deliberate floor.** Hand-written `impl Tool` tools (e.g. `NotesTool`, `MemoryTool`, `TaskTool`, `AskUserTool`) and **MCP tools** take `&RoutingContext` directly because the registry dispatches one fixed `Tool::execute(args, &RoutingContext)` signature; there is no per-tool `Ctx` slot. `McpTool` *cannot* be narrowed at all — its schema is fetched from a remote server at runtime, so it can never use `#[derive(Tool)]`. 12 of the 17 hand-written tools already ignore `ctx` (`_ctx`), so their dependency is already visibly "nothing"; converting their hand-rolled multi-action dispatch to a typed path purely to write `type Ctx = ()` is high-effort, low-value churn and is intentionally **not** done. A future architecture review should treat these as a recorded, deliberate boundary — not a gap.

Migration is incremental and always-green. Phase A adds the machinery and sets `type Ctx<'a> = FullCtx<'a>` on all 12 impls (mechanical; behavior identical — `FullCtx` derefs to `RoutingContext`). Later phases narrow tools rung-by-rung: the 5 filesystem read tools to `HookCtx`, the 6 write/edit/web/plan tools to `IoCtx`, leaving `bash` on `FullCtx`. Each per-tool narrowing is independently revertible. `bus::InjectorContext` stays implemented on `RoutingContext`; the bus injection layer is untouched.
